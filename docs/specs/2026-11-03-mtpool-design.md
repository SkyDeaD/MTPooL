# MTPooL: спецификация первой версии

Дата: 2026-11-03. Статус: согласована.

MTPooL поддерживает работающую группу MTProto-прокси за постоянными доменами. Серверы сами регистрируются в пуле по токену. Пул следит за их здоровьем, выбирает мастеров, ведёт DNS в Cloudflare и банит IP только после подтверждения независимыми сенсорами. Команда пишет своих ботов на открытом API.

Проект написан с нуля по образцу [sharedd](https://github.com/ugDeDe/sharedd) (MIT, ugDeDe). Код не копируется, поведение и идеи берутся осознанно. Автор sharedd упоминается в README и в `NOTICE`.

## 1. Рамки

### Входит

- Регистратор и агент на Rust, один публичный репозиторий, лицензия MIT.
- Функции sharedd без кабинета: очередь, мастера, ротация, карантин, бан, DNS, СРМД, antiscan, история, дашборд, панель, статистика, ссылки.
- Бан по схеме «карантин → сенсоры → 2 из 3» внутри пула.
- Движки семейства telemt: telemt, MTProxyL, MEKO.
- Токены вместо аккаунтов, токены ботов, webhooks, `/metrics` для Prometheus.
- Полностью новый дизайн, публичная документация API, CI/CD с автообновлением регистратора и агентов.
- Интерфейс и документация на русском, README на русском и английском.

### Не входит

- Кабинеты, аккаунты, инвайты, логины и пароли.
- Покупка и замена VPS, профили, флот, интеграции с хостингами. Этим занимаются боты команды.
- Совместимость со старым API и перенос истории: пул стартует с нуля на новом домене.
- `mtdd` и другие движки вне семейства telemt: появятся позже через адаптер.
- Несколько регистраторов одновременно и внешняя база данных.
- Запуск агента не от root.

### Внутреннее устройство регистратора

Причины выбора — проблемы sharedd: запись всего состояния на каждый отчёт под общей блокировкой и Cloudflare внутри цикла выбора.

- **Владелец состояния.** Одна задача получает команды из очереди и вызывает чистую функцию `core::apply(state, command, now) -> effects`. Функция не обращается к сети и диску, время передаётся параметром.
- **Эффекты.** Запись в базу, DNS, сенсоры, webhooks выполняются отдельными воркерами. Результат возвращается новой командой. Медленный внешний сервис не задерживает выбор мастеров. Перед применением результата проверяется Generation ноды.
- **Чтение.** После каждого изменения публикуется неизменяемый снимок (`ArcSwap`) с готовым JSON и ETag. Публичный API не обращается к владельцу состояния.
- **Запись на диск.** Один поток-писатель, WAL. Регистрации, баны, токены и настройки пишутся сразу с `synchronous=FULL`. Heartbeat, отчёты и счётчики пишутся пачкой раз в 15 секунд и при остановке.
- **Рестарт.** Состояние восстанавливается из базы. В течение одного heartbeat TTL после старта ноды не считаются пропавшими. Битая база или неизвестная версия схемы останавливают запуск с понятной ошибкой.
- **Ошибка записи** переводит `/readyz` в 503 и пишет событие, а не только строку в лог.

## 4. Жизненный цикл ноды

```
              enroll
                │
                ▼
             Pending ──первый верный отчёт──► Healthy ◄───────┐
                │                               │            │
                │ триггер                       │ триггер    │ чистый раунд
                ▼                               ▼            │
             ┌───────────── Quarantine ──────────────────────┘
             │             │             │
    не жива 10 мин     ≥2 голоса      нет решения 60 мин
             ▼             ▼             ▼
           Dead          Banned        Pruned
             │             │             │
          24 часа    запись удалена    24 часа
             ▼          сразу            ▼
       запись удалена      │       запись удалена
                           │
     новая регистрация с этого IP: reverify чистый
                           ▼
                        Pending
```

### Healthy

Нода может быть мастером, только если одновременно верно:

- TCP-защёлка в норме. Регистратор проверяет порт раз в 5 секунд с таймаутом 3 секунды, защёлка падает после 3 неудач и поднимается после 2 успехов.
- Защёлка метрик в норме: те же значения 3 и 2 по отчётам агента.
- Нода доступна из РФ: последняя проверка Globalping подтверждена регистратором и успешна либо действует подтверждение из РФ.
- Порт совпадает с настройкой пула.
- Heartbeat моложе TTL 60 секунд, отчёт с проверенным замером моложе срока годности. Срок годности — большее из `report_max_age_sec` (15 минут) и трёх интервалов замера Globalping: один пропущенный замер не уводит ноду в карантин. Если действует три интервала, панель настроек это показывает.
- Агент не отказался от конфигурации пула из-за занятого имени (`pool_user_taken`, см. раздел о настройке движков).

Нода, для которой любое условие перестало выполняться, переходит в Quarantine: это триггер.

**Подтверждение из РФ.** Раунд, в котором RedFlag и check-host не дали ни одного `Blocked` и хотя бы один из них дал `Clear`. Действует 20 минут. Причина такого условия: пробы Globalping могут не доходить до ноды из-за чужого фильтра, а RedFlag и check-host видят её так, как видят в России.

**Globalping не согласен.** Нода работает при красном Globalping, пока действует подтверждение из РФ. Она может быть мастером, в карточке показана пометка. Проверка из РФ повторяется раз в 15 минут, каждая записывается как раунд:

- подтверждение получено: нода работает дальше;
- хотя бы один `Blocked` от RedFlag или check-host: Quarantine и сразу раунд. Раунд здоровой ноды бана не даёт, решает следующий раунд в Quarantine;
- нет ни `Clear`, ни `Blocked`: повтор через 5 минут, а когда подтверждение истекло, Quarantine.

Зелёный Globalping снимает пометку и останавливает эти проверки. На ноде с чужим фильтром (см. раздел о Globalping) Globalping не учитывается совсем: ей всегда нужно подтверждение из РФ, и проверка идёт раз в 15 минут постоянно. Если RedFlag и check-host не ответили, уже полученное подтверждение продлевается до их ответа: признаков блокировки у такой ноды нет, а сбой сенсоров не должен выводить её из работы.

Порядок в очереди: `queued_at`, `registered_at`, `node_id`.

### Quarantine

При входе нода сразу снимается с мастеров. Назначение домена меняется на следующем тике выбора.

Сначала проверяется живость: heartbeat моложе TTL и TCP-порт открыт снаружи.

- **Не жива.** Сенсоры не запускаются: упавший сервер не считается заблокированным. Через 10 минут непрерывно нежива нода становится `Dead`. Её IP не блокируется, повторная регистрация свободна.
- **Жива, доступна из РФ, не выполнено другое условие** (метрики, порт, устаревший отчёт). Сенсоры не запускаются: блокировкой это не пахнет, а их лимиты ограничены. Как только все условия Healthy выполнены, нода сразу возвращается в Healthy. Устаревший отчёт тоже не подозрение: замер мог не прийти из-за лимита Globalping. Первый свежий зелёный замер возвращает ноду, красный без подтверждения из РФ запускает раунды.
- **Жива, не выполнено условие `pool_user_taken` или порт не совпадает с настройкой пула.** Сенсоры не запускаются, даже если Globalping провален: секрета и домена пула на ноде нет либо сенсоры проверили бы не тот порт, и такой голос не может считаться за бан.
- **Жива, последний замер Globalping провален или его нет, подтверждения из РФ нет.** Нода подозревается в блокировке, сразу запускается раунд сенсоров: всегда вместе RedFlag и check-host. Интервал 5 минут, после 3 раундов без решения 15 минут. Свежий зелёный замер запускает раунд сразу, не дожидаясь интервала. Подозреваемая нода выходит только по чистому раунду: один зелёный замер её не возвращает, а красный Globalping возврату не мешает. Первый раунд запускается сразу, поэтому возврат занимает около двух минут: столько ждётся результат check-host.

В интерфейсе подозреваемая нода показывается как «Карантин», остальные ноды в этом состоянии как «Вне очереди». API отдаёт это полем `suspected`.

Итог раунда:

| Голоса | Решение |
|---|---|
| `Blocked` ≥ 2 | `Banned` |
| от RedFlag и check-host нет `Blocked`, хотя бы один дал `Clear`, все условия Healthy, кроме доступности из РФ, выполнены | чистый раунд → `Healthy` |
| остальное | ждём следующий раунд |

Один `Blocked` от Globalping чистому раунду не мешает, но вместе с `Blocked` от любого другого сенсора даёт бан. На ноде с чужим фильтром Globalping даёт `Abstain`, поэтому для бана нужны и RedFlag, и check-host.

Если решения нет 60 минут, нода становится `Pruned`: IP не блокируется, повторная регистрация получает 429 с паузой 15 минут, затем 30 минут, 1, 2 и 3 часа. Учёт ведётся по `node_id` и IP, пауза сбрасывается при возвращении в очередь, записи удаляются через 7 дней. Так ограничен расход лимитов сенсоров, а нехватка сенсоров не приводит к бану.

### Banned и reverify

Бан заносит IP в `ip_blocks` с паузой до первой проверки и в том же `apply` удаляет запись ноды и её токен, слоты мастера освобождаются. Следующий запрос агента получает 401. Запись в `bans` содержит все голоса. `bans`, `events`, `sensor_rounds` и `node_samples` остаются.

Записи `Dead` и `Pruned` с токенами удаляются через 24 часа после входа в это состояние. Записи `Banned` из старых баз удаляются первой командой после загрузки.

Регистрация с заблокированного IP до конца паузы (`reverify_pause_sec`, 15 минут) получает 429. После паузы она создаёт ноду в режиме reverify и немедленно запускает решающий раунд:

- чистый (`Blocked` = 0, `Clear` ≥ 2, Globalping здесь тоже считается) → событие `ban.lifted`, блокировка снята, нода в Pending;
- иначе блокировка остаётся, запись ноды удаляется, следующая попытка через 15 минут (ответ 429).

Администратор может снять бан вручную, в том числе когда записи уже нет: блокировка находится по `node_id` или по открытой строке `bans`. Действие попадает в аудит.

### Лимит нод владельца

Решение принимает `core`, лимит передаётся в команде `Enroll`. Сначала отказы по адресу (блокировка, пауза). Живая нода на том же IP уступает место новой, отдельного места для этого не нужно. Если лимит занят ровно и у владельца есть запись `Pending`, `Healthy` или `Quarantine` с heartbeat старше TTL, дольше всех молчащая становится `Dead` (`node.dead` с `replaced_by` и `reason: silent`), новая входит. Иначе `403 owner_limit`. Нода с заблокированного IP никого не вытесняет. В первые TTL heartbeat после запуска регистратора вытеснения нет: последние heartbeat могли не дойти до диска.

Смена IP сбрасывает состояние ноды: это новая проверка.

## 5. Сенсоры

Каждый сенсор реализует `vote(target) -> Blocked | Clear | Abstain(причина)` и хранит доказательство. Незаданный ключ означает `Abstain(not_configured)`. Ошибка, таймаут, лимит или незнакомый ответ тоже означают `Abstain`. Сенсор никогда не голосует за бан из-за собственной неисправности.

### Globalping

- Запрос: `http`, HTTPS, HEAD, цель — IP ноды, `request.host` равен SNI ноды, страна RU, тег `eyeball-network`, `limit` 20. Поле `host` действительно уходит в TLS SNI: проверено экспериментом.
- Успех пробы: статус `finished` и в результате есть данные TLS. HTTP-код не учитывается: ответ 403 при пройденном рукопожатии считается успехом.
- Проб с результатом меньше 10 → `Abstain`. Больше половины проб с результатом получили отказ в соединении (`ECONNREFUSED`) → `Abstain(port_refused)`: порт закрыт, это не блокировка. Для здоровья ноды такой замер означает «нет данных». Иначе доля успеха меньше 0,5 → `Blocked`, иначе `Clear`.
- Плановые замеры создаёт сам агент на квоту своего IP. При интервале 300 секунд это 12 замеров × 20 проб = 240 из 250 разрешённых в час. Анонимный лимит считается по адресу, а для IPv6 один счётчик на всю /64, поэтому агент обращается к API Globalping только по IPv4: у соседних нод в одной /64 квота не становится общей. Регистратор скачивает замер и проверяет сам: id, тип, цель, порт, SNI, страну каждой пробы, их число и время создания. Отчёт старше окна −10/+1 минута отвергается. Один `measurement_id` нельзя использовать дважды.
- Внеочередной замер делается по просьбе регистратора: поле `measure_now` в ответе sync. Регистратор просит, когда отчёт с замером старше интервала плюс минута или нода подозревается в блокировке. Агент переносит ближайший плановый замер на сейчас, но не раньше 5 минут после начала предыдущего и не раньше интервала после ответа 429. Внеочередной замер сдвигает расписание, поэтому замеров не больше 12 в час: 240 проб из 250. Сразу после регистрации агент делает замер без ожидания, этим результатом пользуется и reverify. Готовый замер агент отправляет не дожидаясь очередного отчёта, ближайшим тактом heartbeat. Отчёт без нового замера не меняет последний вердикт.
- Ответ 429 от Globalping агент передаёт как «нет данных». Это не провал проверки и не триггер карантина. Если других причин нет, нода остаётся в прежнем состоянии до устаревания отчёта. Причину, по которой замера нет (лимит, недоступность, таймаут), агент и регистратор пишут в журнал.
- Голос раунда берётся из верного отчёта младше 10 минут. Только если такого нет, регистратор создаёт замер сам с токеном `GLOBALPING_TOKEN`.
- Перед таким замером регистратор смотрит `/v1/limits` (запрос бесплатный). Лимит аккаунта 500 тестов в час общий для всех его токенов, а сверх лимита Globalping автоматически списывает кредиты. Настройка `globalping.allow_credits`, по умолчанию выключена: при остатке меньше 20 сенсор даёт `Abstain` и кредиты не тратит.
- Токен Globalping на ноды не передаётся. Иначе все ноды делили бы один лимит аккаунта: 9 нод дали бы 2 160 тестов в час.
- В доказательство для каждой пробы пишется код причины провала: `timeout`, `refused`, `tls`, `other`. Текст ошибки Globalping не сохраняется: в нём бывает адрес ноды, а доказательство показывается публично.
- **Чужой фильтр.** Другой пул на той же ноде может заставлять её отбрасывать адреса из своего списка, а среди них бывают адреса проб Globalping. Проверить это по адресам нельзя: Globalping их не отдаёт. Поэтому агент раз в 30 минут ищет в `iptables-save` правило, которое отбрасывает соединения на порт пула по набору `ipset`, в том числе через переход в отдельную цепочку. Ищется сама конструкция, а не имя набора. Собственная цепочка `ANTISCAN_MTPOOL` чужим фильтром не считается: на ноде с работающей цепочкой Globalping дал 20 успехов из 20 в трёх замерах подряд (проверено на одной ноде 2026-11-08). Найденное агент передаёт в отчёте полем `port_filter` с именем набора. Пока фильтр есть, голос Globalping для этой ноды `Abstain(port_filter)`, причина показана в панели. Правила вне `iptables-save` (чистый nftables) агент не увидит: тогда работает обычный путь через подтверждение из РФ. Отчёт о фильтре присылает сама нода, и злоупотребить им можно: она избавится от голоса Globalping. Для бана всё равно нужны два других голоса, поэтому этот риск принят.

### check-host

- Проверяется TCP-соединение с двух точек в Москве: `ru1.node.check-host.net` и `ru2.node.check-host.net`, это разные автономные системы. Список точек зашит в код. TLS и SNI сервис не проверяет.
- Цель: IP ноды и порт SSH, по умолчанию 22. Сенсор отвечает на вопрос, закрыт ли из РФ сам адрес. Порт пула для этого хуже: на нём стоит чужой фильтр, и он зависит от движка. Проверено на ноде в карантине 2026-11-08: порт 22 соединился с обеих точек, порт 443 только с одной.
- Порт задаётся на ноде настройкой `check_host_port` в `agent.toml`, агент передаёт его с результатом. Значение 0 отключает проверку: голос `Abstain(not_configured)`. Отключать нужно там, где SSH закрыт фаерволом для РФ или на этой ноде нет SSH снаружи.
- Контроль живости порта. Перед подсчётом голоса регистратор сам открывает соединение с этим портом снаружи РФ. Не открылось → `Abstain(port_closed)`: порт закрыт или перенесён, блокировкой это не считается.
- Проверку запускает агент с адреса своей ноды: лимит сервиса считается по адресу. `GET https://check-host.net/check-tcp?host=<ip>:<port>&node=<ru1>&node=<ru2>`, заголовок `Accept: application/json`, свой `User-Agent`: стандартный `Python-urllib` получает 403. Ключа и платного тарифа у сервиса нет, лимиты не опубликованы.
- Проверка запускается всегда вместе с RedFlag. Регистратор просит её полем `check_host_now` в ответе sync. Агент запускает проверку не чаще раза в 5 минут, после ответа `limit_exceeded` делает паузу 20 минут и передаёт «нет данных». Готовый id агент отправляет в поле отчёта `check_host` ближайшим тактом heartbeat. Сразу после регистрации агент проверяет себя без просьбы, этим результатом пользуется и reverify.
- Регистратор сам скачивает `GET https://check-host.net/check-result-extended/<id>` и сверяет: `command` равен `tcp`, `host` равен IP ноды, `port` равен переданному порту проверки, в `results` обе точки, `created` в окне −10/+1 минута. Один id нельзя использовать дважды. Значение `null` у точки значит, что она ещё работает: ответ читается повторно до 30 секунд. Чтение результатов лимит запусков не расходует: это проверено на 14 чтениях подряд.
- Голос раунда берётся из верного результата младше 10 минут, которого не было в прошлом раунде этой ноды: один результат не идёт в два раунда. Если такого нет, регистратор просит новую проверку и ждёт её до 110 секунд, не задерживая владельца состояния: весь раунд ограничен 120 секундами. Результата нет → `Abstain(no_data)`.

| Результат двух точек | Голос |
|---|---|
| обе соединились: `[{"address":…,"time":…}]` | `Clear` |
| обе `Connection timed out` | `Blocked` |
| остальное: разный результат, `Connection refused`, лимит, нет ответа, незнакомая ошибка | `Abstain` |

- Отдельной точки за пределами РФ нет. Упавшую ноду отсекает проверка живости, а закрытый порт SSH отсекает контроль регистратора.
- В доказательство пишутся код результата и время соединения каждой точки. Адрес ноды из ответа сервиса не пишется.
- Голоса прежнего сенсора cheburcheck, снятого с голосования, остаются читаемыми в истории раундов и банов.

### Чекер RedFlag

- `POST https://api.yazaebalsyadelatproxy.cc/v1/check?mode=sync&timeout=15`, заголовок `X-API-Key` из `REDFLAG_API_KEY`, тело `{server, port, secret}`. `server` — IP ноды, а не домен: проверяется конкретный сервер. `secret` — публичный секрет пула в формате ссылки.
- Значения по документации автора бота:

| Статус | Что значит | Голос |
|---|---|---|
| `OK` | данные доходят до DC из РФ и снаружи | `Clear` |
| `DATA_CUT` | снаружи работает, из РФ хендшейк проходит, поток до DC режется | `Blocked` |
| `RKN_BLOCK` | снаружи работает, из РФ не проходит хендшейк или TCP | `Blocked` |
| `MT_DEAD` | снаружи поток не доходит при живом TCP: сервис деградировал или DPI у хостинга | `Abstain` |
| `DOWN` | сервер недоступен полностью | `Abstain` |
| `UNKNOWN` | нестандартная картина | `Abstain` |

- `MT_DEAD` и `DOWN` не считаются блокировкой из России: это неисправность сервера или сети снаружи. Они показываются в карточке ноды рядом с голосами.
- В доказательство сохраняются `status`, `checked_at`, блоки `local` и `remote` с `tcp`, `handshake`, `data`, `latency_ms`.
- Точка проверки «из РФ» одна: нода бота. Блокировку только на мобильном ТСПУ сенсор может не увидеть, поэтому его голос не решает в одиночку.
- Лимит сервиса 30 запросов в минуту на ключ. Лимитер пула — 20 в минуту. Коды 401, 403, 429, 502, 503 и таймаут дают `Abstain`, при 429 соблюдается `Retry-After`. 401 и 403 показываются как `key_rejected`: ключ не принят.

### Расширение

Голосуют Globalping, RedFlag и check-host. Новый сенсор добавляется реализацией того же интерфейса. Правило «2 голоса `Blocked`» не меняется и не зависит от числа сенсоров.

## 6. Выбор мастеров и DNS

### Выбор

Чистые функции из `core`, тик раз в 3 секунды:

- Назначить мастера на свободный слот: наименее загруженный, затем по очереди, IP на домене различаются.
- Ротация по времени: по умолчанию 30 минут, не больше 43 200, 0 выключает. За тик меняется один слот на домен, заменённая нода уходит в хвост.
- Заменить снятого мастера.
- Нода без доменов может забрать один слот у самого загруженного донора. Полной перебалансировки нет.
- Пустая очередь не очищает назначения.
- `masters_per_domain` от 1 до 8.

### DNS

- Модель desired/applied с Generation на домен. Backoff 5 с·2^n, максимум 5 минут.
- Порядок: сначала создать новые записи, затем удалить лишние. Запись-конфликт удаляется только тогда, когда этого требует тип записи.
- A-записи с TTL 60 и настройкой proxied. CNAME для свёрнутых доменов. Нижняя граница настройки TTL 60 секунд: значение 1 у Cloudflare значит «автоматически», это 300 секунд.
- Каждая запись пула несёт комментарий `MTPooL`. По нему пул отличает свои записи и видит их только под именами своих доменов; другие записи зоны он не читает и не меняет.
- Удаляются только записи, которыми пул управлял сам, и только типов A, AAAA, CNAME.
- Пустой desired считается ошибкой и не применяется.
- Лимитер на Cloudflare: 3 запроса в секунду при лимите 1 200 за 5 минут. На запрос таймаут 15 секунд.

### СРМД

По умолчанию выключен.

- `нужно = max(1, ceil(очередь / (max_nodes_per_domain × masters_per_domain)))`, `max_nodes_per_domain` по умолчанию 5, максимум 50 доменов.
- Расхождение должно держаться 20 тиков подряд (около минуты), затем одно действие.
- Рост: сначала развернуть свёрнутые домены, затем создать новые с именем `база+N`.
- Сжатие: остаётся `max(нужно, число не созданных СРМД доменов)` первых активных. Остальные начиная с крупных по клиентам сворачиваются CNAME на наименее загруженного выжившего.
- CNAME всегда указывает на активный домен, цепочки выправляются на каждом тике.
- Клиенты домена — сумма по его мастерам. Если метрики нет, берётся последнее известное значение.
- Ручные `take` и `release` из панели, настройки сохраняются.

## 7. Токены и безопасность

| Токен | Выдаёт | Что может |
|---|---|---|
| Админ | установщик, показывается один раз | вход в панель, все операции `/admin` |
| Регистрации | админ, на владельца | только `POST /agent/enroll`, в рамках лимита нод; можно задать срок, можно отозвать |
| Ноды | регистратор при enroll | действия только от имени этой ноды |
| Бота | админ, на владельца | чтение, свои ноды с полными IP, webhooks |
| Метрик | админ | только `/metrics` |

Формат: `mtp_<тип>_<случайная часть>`, чтобы сканеры секретов находили утечки.

- Вход в панель меняет админ-токен на cookie `HttpOnly; Secure; SameSite=Strict` со сроком 7 дней и CSRF-защитой. Ротация токена завершает сессии. Потерянный токен восстанавливается на сервере командой `mtpool-registrar admin reset-token`.
- Неудачные попытки любых токенов ограничены по IP. Клиентский IP берётся из `X-Forwarded-For` только при подключении с loopback от Caddy.
- Сравнение токенов за постоянное время. Секреты не попадают в логи и ответы API, поля настроек с секретами только записываются.
- Лимит запроса 256 КиБ, неизвестные поля отвергаются. Только публичный IPv4. Webhook-адреса только HTTPS, частные адреса запрещены, в том числе после разрешения имени.
- Публичный API отдаёт IP в виде `A.x.x.D` и не показывает `measurement_id`: Globalping раскрыл бы по нему полный адрес.
- Ссылки с секретом открыты всем по решению владельца пула.
- Агент не слушает портов. Запускается от root с песочницей systemd: ему нужно управлять движком, правилами сети и своим бинарником.

### Секреты и публичный репозиторий

- В репозитории только `.env.example`. В `.gitignore` с первого коммита: `.env*` (кроме примера), `tmp/`, базы данных, ключи.
- Прод: `/etc/mtpool/registrar.env` с правами 0600. CI: GitHub Secrets окружения `release`.
- CI запускает `gitleaks` на каждом изменении и на всей истории. PR из форков не получают секретов, `pull_request_target` не используется, self-hosted раннеров нет.

Переменные регистратора: `CLOUDFLARE_API_TOKEN`, `GLOBALPING_TOKEN`, `REDFLAG_API_KEY`, `MTPOOL_PUBLIC_URL`, `MTPOOL_DB_PATH`. Токену Cloudflare достаточно права `Zone → DNS → Edit` на одну зону.

## 8. API `/api/v1`

- Публичные ответы с ETag, 304 и лимитом частоты по IP. При лимите: 429 и `Retry-After`.
- Ломающие изменения только через новую версию пути. CI сравнивает спецификацию с предыдущим релизом.

### История клиентов

Воркер раз в 30 секунд берёт из снимка состояния число клиентов и пишет строки в `client_samples`: сумму по нодам в состоянии Pending, Healthy и Quarantine и клиентов каждого домена из раздела 6. Если метрики нет, берётся последнее известное значение. Владелец состояния сети и диска не ждёт.

Считаются только клиенты пользователей пула, см. раздел 9, «Клиенты и трафик пула». В старых точках осталась сумма по всем пользователям движка.

`GET /stats/clients?range=10m|1h|24h|7d` отдаёт `step_sec`, точки `{at, total, domains}` и отметки `{at, kind}`, где `kind` это `master_change`, `fold` или `ban`. Шаг 30 секунд для `10m` и `1h`, 5 минут для `24h`, 30 минут для `7d`; значение точки — среднее за шаг. Ответ кэшируется на 10 секунд, идёт с ETag. В нём нет IP и имён нод. Если регистратор не работал, в ряду остаётся пропуск: точки не выдумываются.

### Доступность ноды

Воркер раз в 30 секунд отмечает в корзине ноды, работает ли она: `Healthy` считается работающей, `Quarantine` и `Dead` нет, остальные состояния не считаются. Доступность это доля работающих отметок за 30 дней, она пересчитывается раз в 5 минут и лежит в снимке. Нода без отметок показывает прочерк, а не ноль.

### Ответы агенту

- 200 при успехе.
- `403 {terminate, reason, message}`: нода снята.
- `410`: нода неизвестна, нужно зарегистрироваться заново.
- `409`: отчёт устарел, повторён или вытеснен.
- `429` с `Retry-After`: не обращаться раньше срока.

### Webhooks

События: `node.registered`, `node.quarantined`, `node.recovered`, `node.banned`, `node.dead`, `node.pruned`, `ban.lifted`, `master.changed`. Токен бота получает события своих нод. Подписка на весь пул доступна с областью `pool:read`. Журнал панели подробнее webhook: только в нём `node_ip_changed` и `dns_applied` с записанными адресами, а полный IP из `node_registered` в webhook не передаётся.

- Запрос подписан: заголовок `X-MTPooL-Signature: t=<время>,v1=<HMAC-SHA256>`. У каждого события постоянный `id`, поэтому получатель легко отсекает повторы.
- Повторы через 1 минуту, 5 минут, 30 минут, 2 и 6 часов. Журнал доставки виден через API.

| опрос раз в 45 секунд | webhook `node.banned` и `node.recovered` |
| 2 из 3 на стороне бота | готовый вердикт и голоса в `last_round` |
| `POST /register`, `install_node_web.sh` | `POST /agent/enroll`, `install.sh` |
| юнит `sharedd-node-agent` | юнит `mtpool-agent` |

Подробное руководство по переносу бота: [bots.md](../bots.md). proxy-rotator в этот проект не входит.

## 9. Агент

- Настройки в `/etc/mtpool/agent.toml`, состояние в `/var/lib/mtpool/`: `node_id`, токен ноды и токен регистрации с правами 0600.
- Токен ноды недействителен (401) → файл удаляется, агент регистрируется заново токеном регистрации. Если тот отозван, агент останавливается с понятной ошибкой в журнале.
- Интервалы по умолчанию: heartbeat 15 секунд, Globalping 300, метрики 60, синхронизация 60. Backoff 5 с·2^n, не больше 5 минут, джиттер 50%.
- `403 terminate` → агент прекращает отчёты и движок не трогает. Повторяет регистрацию раз в 15 минут.
- Бан: запись и токен удалены, агент получает 401, регистрируется заново и выжидает паузу по `Retry-After`. Это и есть reverify.
- Смена адреса: агент пытается снять старую запись (`/agent/retire`, до 3 секунд, неудача не мешает) и сразу регистрируется. В `429` и после `403 terminate` он тоже следит за адресом и при смене регистрируется, не дожидаясь паузы.

### Адаптер движка

Интерфейс: `detect`, `apply_config`, `metrics`, `health`. Определение по файлам: `/opt/mtpr-simple` — MEKO, `/opt/mtproxyl` — MTProxyL, иначе telemt.

Здоровье telemt:

- Метрики с `/metrics`: `telemt_me_writers_active_current`, `telemt_user_unique_ips_current{user}`, `telemt_user_connections_current`, `telemt_user_octets_{from,to}_client[_total]`.
- При заданном Control API проверка DC2 через `/v1/stats/dcs`: причины `dc2_api_error`, `dc2_me_disabled`, `dc2_stale` (старше 300 секунд или из будущего больше чем на 120), `dc2_absent`, `dc2_no_endpoints`, `dc2_no_fresh`.
- Трафик считается дельтами с обработкой сбросов счётчиков. Что именно считается, описано в разделе «Клиенты и трафик пула».

Применение настроек в telemt и MEKO: правка `toml_edit` с сохранением форматирования, проверка, атомарная запись. MTProxyL настраивается только через свою CLI (`mtproxyl secret`, `mtproxyl expert`, `mtproxyl restart`): она пересобирает `config.toml`, а простой `systemctl restart` поднял бы старый конфиг. Если движок надо перезапустить: stop → запись → start → ожидание метрик до 60 секунд → откат при неудаче.

Конфиг владельца сервера дополняется, а не перезаписывается. Штатная ссылка сервера продолжает работать, и та же нода обслуживает пул. Правила одинаковы для всех движков:

- **Пользователи.** Пул добавляет своих рядом с пользователями владельца и удаляет только тех, кого добавил сам. Чужую запись пул не занимает. Если в движке уже есть пользователь с именем из `proxy_users` и другим секретом, а в `pool_users.json` этого имени нет, агент не применяет конфигурацию пула целиком и ничего не меняет в движке. В журнал идёт имя без секрета, в отчёт `error: pool_user_taken`. Регистратор ведёт это как условие Healthy: нода сразу уходит в Quarantine, а когда имя освободится, следующая синхронизация применит конфигурацию и нода вернётся. Если этого не случится за 60 минут, нода становится `Pruned` по общему правилу. Запись с тем же секретом считается записью пула: так агент находит её после потери файла состояния. Плохой `pool_users.json` читается как пустой, поэтому ротация секрета на такой ноде тоже даст отказ.
- **`tls_domain`** записывается, только если ключа нет. Существующее значение не меняется.
- **`tls_domains`.** SNI пула добавляется, если он не совпадает с `tls_domain`. Записи владельца остаются. При смене SNI удаляется только прежний домен пула.
- **`exclusive_mask`.** Если в `[censorship]` явно стоит `mask = true`, а для MTProxyL всегда, добавляется запись `"<SNI>" = "<SNI>:443"`. Записи владельца остаются. При смене SNI удаляется только прежняя запись пула.
- **Порт** агент не меняет ни в `[server]`, ни в `listeners`. Нода с другим портом сообщает свой порт, получает `port_ok = false` и в пул не входит, а её штатная ссылка продолжает работать.
- **Слушатель метрик** добавляется, только если в файле его нет.
- Если менять нечего, файл не перезаписывается и движок не перезапускается.

### Клиенты и трафик пула

На ноде рядом с пользователями пула работают пользователи её владельца, и пул не может ими распоряжаться. Поэтому пул везде считает только своих.

- **Клиент** — уникальный IP, который движок считает для пользователя: `telemt_user_unique_ips_current{user}`. **Трафик** — `telemt_user_octets_{from,to}_client[_total]{user}`.
- **Свои** — пользователи из `settings.proxy_users`, которых агент записал в движок. Их имена лежат в `pool_users.json` и читаются при каждом отчёте, поэтому список следует за настройками и переживает перезапуск агента. Принадлежность определяет только имя. Чужую запись пул не занимает (правило «Пользователи» выше). Запись владельца с тем же именем и секретом считается записью пула: она в движке одна, и разделить её счёт нельзя.
- **Остальные** — все прочие метки `user` у движка. Они идут отдельно: `other_clients`, `other_from_client_total`, `other_to_client_total` в отчёте, `other_clients` и `other_traffic_bytes` у ноды в API.
- Отсутствие серии означает 0, а не ошибку: у пользователя без трафика есть только серии `telemt_user_unique_ips_*`.
- Числа пула не содержат остальных: `client_samples`, `node_samples`, колонки `from_client` и `to_client` в `traffic`, клиенты домена и свёртка СРМД, `traffic_*` в `/stats/*`.
- Трафик остальных хранится рядом, в колонках `other_from_client` и `other_to_client` таблицы `traffic`, и отдаётся отдельно: `traffic_all_time.other_*` в `/stats/summary`. С трафиком пула он не складывается.
- Итог за всё время (`traffic_all_time`) учитывает и ноды, которых в пуле уже нет. Ряды трафика на дашборде не показываются. Счётчик остальных начинается с того, что ноды успели насчитать к обновлению регистратора: раньше он в журнал не записывался.
- Пока список неизвестен (конфигурация ещё ни разу не применилась) или выключена пользовательская телеметрия, агент отправляет нули, `clients: null` и не отправляет `other_*`.

Первая база. Счётчик, в котором только свои, меньше прежней суммы по всем, и обычная обработка сброса прибавила бы его целиком. Поэтому ядро смотрит на вид отчёта: есть ли в нём `other_*`. Если вид изменился по сравнению с сохранённой базой, в любую сторону, чтение только задаёт новую базу, без дельты. Настоящий сброс при неизменном виде по-прежнему считается. Так обновление агента, его откат и период без списка не дают ложного всплеска; трафик между двумя чтениями с разным видом не учитывается.

Историческая ступенька. Точки, записанные до обновления агента на ноде, содержат сумму по всем пользователям движка. Пересчитать их нельзя: разбивки по пользователям в них нет. На графиках клиентов в этот момент возможна ступенька вниз на долю пользователей владельца, она уйдёт по мере истечения срока хранения рядов. В итоге трафика такие значения остаются, потому что он не удаляется.

### Прочие модули

- **Antiscan:** список ipsum уровня 1 раз в 30 минут, `ipset restore` с атомарной заменой, цепочка iptables на все порты. Команды хоста вызываются пачкой через stdin. Отключается настройкой.
- **Определение IP:** 4 внешних сервиса. Проверка смены IP раз в 45 секунд.
- **Локальное здоровье:** 3 плохих проверки подряд — нода замолкает, 2 хороших — возвращается.
- **Dead-kill:** через 10 минут мёртвого состояния вызвать `/agent/retire`.

### Установка

```
curl -fsSL https://<пул>/install.sh | MTPOOL_TOKEN=<токен> sh -s -- --name <имя>
```

- `install.sh` раздаётся регистратором со встроенным публичным ключом и проверяет подпись бинарника. Без валидной подписи установка останавливается.
- Токен передаётся через переменную окружения или `--token-file`, не аргументом: аргументы видны в `ps`.
- Сервер и порт пула берутся из настроек регистратора. Если порт движка не совпадает с настройкой пула, установка завершается с ошибкой.
- Установщик показывает шаги на русском, ждёт регистрации (60 секунд, иначе код 1) и признания ноды `Healthy` (3 минуты, иначе код 0 и сообщение, что проверка идёт), вывод программ пишет в `/var/log/mtpool/install.log` с доступом только для root.
- Необязательный `--preset telemt|mtproxyl` ставит движок официальным установщиком. MEKO только определяется.

## 10. Интерфейс

### Публичные страницы

- **Статистика:** состояние пула, показатели, график клиентов, схема доменов и мастеров, таблица нод с группами «Мастера», «В очереди», «Карантин», «Вне очереди», «Регистрируются». В последней группе ноды `Pending`: они на странице, но в счётчики нод и сумму «своих» не входят, пока не вошли в пул. Забаненных нод в таблице нет: бан виден в истории банов на дашборде.
- **Дашборд:** баны за период, причины, время жизни, трафик за всё время: пользователи пула и отдельно пользователи владельцев нод.
- **Ссылки:** прокси-ссылки с QR-кодом, сформированным на сервере.
- **API:** статические страницы из OpenAPI, примеры curl и webhook, руководство для ботов. Интерактивная проверка загружается только по клику.

Страницы пререндерятся в статику, данные обновляются опросом раз в 30 секунд с ETag. Числа клиентов приходят потоком `GET /stream`: раз в 5 секунд, а при изменении пула страница перечитывает списки, но не чаще раза в 15 секунд: запросы одного адреса ограничены. Один воркер делает кадр из опубликованного снимка, поэтому работа не растёт с числом зрителей, а владелец состояния о потоках не знает. Число потоков ограничено на адрес и на весь сервис. Поток заканчивается сам через случайный срок от 15 до 30 минут, чтобы даже исправно читающий клиент не держал место вечно, а браузер открывает новый после паузы `retry`: у каждого потока она своя, от 5 до 15 секунд, чтобы вкладки не возвращались разом после перезапуска. Без потока страница работает на опросе. На скрытой вкладке поток закрыт. Линия графика плавно идёт между точками.

### Панель

Вход по токену. Разделы: Обзор, Ноды, Страница ноды (с голосами сенсоров по раундам), Мастера и DNS, СРМД, Журнал, Настройки, Владельцы и токены, Обновления. Живые данные через SSE. График клиентов использует тот же `GET /stats/clients`, что и публичная страница. В таблице нод группа «Карантин» идёт первой, за ней «Вне очереди». Забаненная нода не показывается ни в таблице нод, ни в счётчиках, ни в «Требует внимания»: сервер обычно пересоздают или меняют ему IP, а смотреть на такую запись незачем. Бан лежит в истории банов и журнале. Из истории открывается страница ноды с голосами сенсоров и кнопкой «Снять бан».

В настройках понятные названия вместо ключей конфига, секунды и минуты вместо миллисекунд, одна кнопка сохранения на форму.

Запрещено то, что делало прежний интерфейс «детским»: стекло, размытие, градиентные рамки и кнопки, цветные плитки с иконками, эмодзи, бейджи без смысла, пустые KPI-карточки, обрезанные таблицы.

**Выбранное направление:** строгий корпоративный инструмент, плитки на ровном фоне. Утверждено пользователем 2026-11-04 на рабочем прототипе.

- **Палитра.** Один синий акцент: `#5aa5ff` в тёмной теме, `#0b63e5` в светлой. Фон `#0c0e13` и `#f2f4f7`, плитка `#14171e` и `#ffffff`. Цвет состояния только для исключений. Ряды графика: `#3987e5 #d95926 #199e70 #c98500`, серый `#4b5262` в тёмной теме; `#2a78d6 #eb6834 #1baf7a #eda100`, серый `#aeb5c2` в светлой. Значения живут в `web/src/styles/tokens.css`.

## 11. Поставка

```
PR ──► CI: rustfmt, clippy -D warnings, тесты, cargo-deny,
           UI-проверки и бюджет, OpenAPI diff, shellcheck,
           gitleaks, Docker e2e

Кнопка релиза (версия)
  └► тег → сборка amd64 и arm64 musl → подпись minisign
     → SBOM, аттестация GitHub → GitHub Release

Регистратор замечает релиз
  └► скачивает, проверяет подпись → обновляется
     → /readyz 60 с, при сбое откат
     └► раздаёт агентам: канарейка → партии → стоп при сбое
```

- Обновление **только pull**: SSH-ключей к серверам в CI нет.
- Регистратор проверяет GitHub Releases раз в 5 минут, хранит файлы у себя и раздаёт агентам сам.
- Подпись minisign, публичный ключ встроен в бинарник и `install.sh`. Закрытый ключ в GitHub Secrets окружения `release`, доступного только запуску релиза. Новый ключ вводится релизом, подписанным старым.
- Раскатка: канарейка — одна здоровая нода не мастер, наблюдение 10 минут, затем партии по 10% раз в 5 минут. Нода не вернулась за 120 секунд или здоровье упало → раскатка останавливается, в панели кнопки «продолжить» и «отменить». Движки не перезапускаются при обновлении агента.
- Агент раздаётся, только если его версия не новее регистратора. После отката регистратора незаконченная раскатка более нового агента отменяется, манифест в каталоге релизов её не возобновляет.
- Регистратор хранит релиз, который может раздать. Последний релиз не новее самого регистратора публикуется в каталог без самообновления, если там нет релиза или лежит более старый. Поэтому первую ноду можно поставить сразу после установки регистратора, не дожидаясь следующего релиза. Версия, отклонённая после отката, не публикуется.
- Откат на сервере: предыдущий бинарник хранится рядом, переключение через `OnFailure` юнита systemd. Перед миграцией схемы база копируется в `<база>.before-v<версия>`, без копии миграция не начинается. Сборка, вернувшаяся откатом, находит базу новее себя и забирает копию моложе 10 минут; в остальных случаях она отказывается запускаться, и копию возвращают вручную.
- Совместимость агента и регистратора. Порядок «сначала регистратор» не гарантирован: релиз лежит в каталоге релизов ещё до перезапуска регистратора и остаётся там после его отката, а ноды, обновившиеся до отката, остаются на новой версии. Поэтому новый агент может говорить со старым регистратором, и наоборот. Отчёт и его `metrics` не отказывают из-за незнакомых полей. Новое поле отчёта, которое старый регистратор отверг бы, агент отправляет только после того, как `GET /agent/config` подтвердил поддержку (`report_other_users`). Так же подтверждается поддержка `check_host` и `port_filter` (`report_check_host`). Без подтверждения агент отправляет отчёт прежнего вида. Новая нода агента новее регистратора не получает. В каталоге лежит один релиз, поэтому при манифесте новее регистратора `GET /releases/manifest.json` отвечает 409 с кодом `registrar_behind`, а `install.sh` останавливается с объяснением и ничего не ставит. Установка снова работает, когда регистратор дойдёт до этой версии.
- Перезапуск регистратора: systemd socket activation, соединения ждут в очереди сокета.
- Actions закреплены по SHA, зависимости обновляются ботом через PR.
- Первая установка регистратора: `install-registrar.sh` на Ubuntu 24.04 (Caddy, unit-файлы, база, выдача админ-токена). Требования: 1 vCPU, 1 ГБ RAM, публичный IPv4 (оценка, уточнится нагрузочным тестом).
- Резервная копия: ежедневный `sqlite .backup` с контрольной суммой. Процедура восстановления описана и проверена в e2e.

## 12. Тестирование

| Уровень | Что проверяет | Где |
|---|---|---|
| Unit и property | `core`: автомат, выбор, СРМД, правила бана, с подменой времени | `cargo test` |
| Контракт сенсоров | разбор записанных ответов Globalping, check-host, RedFlag | `cargo test` |
| Интеграция | HTTP и SQLite регистратора с заглушками внешних сервисов | `cargo test` |
| E2E | регистратор и агенты в Docker: настоящий telemt, systemd, iptables, ipset, потери через `tc netem`, заглушки сервисов | Mac и CI |
| UI | Playwright: сценарии, тёмная и светлая темы, ширина 360 px, доступность | CI |
| Нагрузка | 1 000 симулированных нод на регистратор | CI по запуску |
| Реальная проверка | VPS и настоящая нода: Globalping, пробы, Cloudflare, блокировки | перед первым релизом |

Обязательные E2E-сценарии:

- 1 голос `Blocked` не даёт бана, 2 голоса дают.
- Все сенсоры недоступны: бана нет, через 60 минут нода Pruned.
- Globalping красный, RedFlag и check-host дают `Clear`: короткий карантин, один чистый раунд, возврат с пометкой «Globalping не согласен», бана нет.
- Нода с пометкой получает `Blocked` от check-host: снова Quarantine и раунды.
- На ноде с чужим фильтром красный Globalping даёт `Abstain`; один `Blocked` не даёт бана, `Blocked` от RedFlag и check-host даёт.
- check-host: обе точки таймаут дают `Blocked`; разный результат, `Connection refused`, `limit_exceeded` и незнакомая ошибка дают `Abstain`. Порт, закрытый и для регистратора, даёт `Abstain(port_closed)`. Результат с чужим адресом, портом или повторным id отвергается.
- Globalping отвечает 403 с успешным TLS: нода здорова.
- Выключенный движок становится Dead, а не Banned.
- Cloudflare недоступен: выбор мастеров продолжается, DNS применяется после восстановления, старые записи не удалены раньше времени.
- Рестарт регистратора под нагрузкой: состояние восстановлено, ложных смертей нет.
- Ошибка записи в базу видна в `/readyz`.
- Обновление с неверной подписью отвергается; неудачное обновление откатывается и останавливает раскатку.
- Reverify снимает бан при чистом раунде и держит его при плохом.

## 13. Цели по скорости

Первый замер может их уточнить, изменения фиксируются в этом документе.

- Регистратор при 1 000 симулированных нод на 2 vCPU: p99 heartbeat меньше 20 мс, p99 публичного `GET /api/v1/nodes` меньше 20 мс.
- Агент: RSS меньше 20 МБ в покое, бинарник меньше 15 МБ.
- Публичная страница на эмуляции слабого телефона (троттлинг CPU 4×, медленная сеть): LCP меньше 2,5 секунды, INP меньше 200 мс.

## 15. Что проверить при реализации

Заранее подтвердить невозможно, но решения от этого зависят:

| Вопрос | Как проверить | Если не подтвердится |
|---|---|---|
| Какие поля TLS отдаёт Globalping при недействительном сертификате маски | реальный замер | уточнить критерий успеха |
| Виден ли бан на порту 22 у живой заблокированной ноды | все забаненные адреса 2026-11-08 не отвечают даже извне РФ, сравнить не на чем; проверить порт 22 и порт пула на первой такой ноде | проверять порт пула, если блокировка на порт 22 не действует |
| Не считают ли фаервол и fail2ban проверки SSH атакой | наблюдение на нодах: 4 запуска в час с двух адресов, у спорной ноды около 8 из-за дополнительного запуска в каждом раунде, и контроль регистратора | изменить порт или отключить через `check_host_port` |
| Нода, закрывшая SSH только для РФ, даёт ложный `Blocked` | контроль снаружи РФ такого не поймает; смотреть на расхождения с RedFlag | отключить проверку на этой ноде; при частых случаях сделать порт настройкой пула |
| Лимиты check-host | наблюдение: запуски замерены грубо, около 6 с адреса и 15–20 минут до сброса; чтение результатов с адреса регистратора при многих нодах не замерялось | изменить паузы агента, разнести чтения по времени |
| Как часто check-host один даёт `Blocked` при чистых RedFlag и Globalping | статистика раундов | такой раунд ждёт и может дойти до Pruned; смягчить условие чистого раунда |
| Попадают ли точки check-host в antiscan и чужие фильтры | antiscan закрывает и порт 22; сверка адресов со списком ipsum: в ноябре 2026 их там нет | не учитывать голос check-host на такой ноде |
| Видит ли агент правила при своих правах | запуск на настоящей ноде: у службы есть `CAP_NET_ADMIN` | дать нужные права или читать иначе |
| Умеет ли telemt применять пользователей без рестарта | документация и код telemt | Да, `[access.users]` применяется на лету; порт, `tls_domain`, api и метрики требуют рестарта. Агент пока всегда применяет транзакцией с рестартом |
| Подтягивает ли `utoipa-scalar` скрипт с CDN | чтение кода | не использовать, взять RapiDoc |
| Реальный размер публичной части на Svelte | сборка | перейти на askama |
| Есть ли `tnum` у Geist | `ttx -t GSUB` | взять Inter |
| Держат ли операторы длинные SSE | наблюдение | заменить на long-poll |
| Достаточно ли 33 RU eyeball-проб для `limit` 20 | статистика ответов | сделать тег настраиваемым или убрать |

### Что показал выпуск 0.0.8

Замер 2026-11-08, сразу после выпуска. Данных пока мало: 11 раундов, и во всех нода с чужим фильтром, поэтому Globalping в них воздержался. Итог раундов: 10 чистых, 1 без решения, бана нет.

| Вопрос | Результат |
|---|---|
| Видит ли агент правила при своих правах | Да: на пяти настоящих нодах агент нашёл чужой ipset и прислал его имя |
| Лимиты check-host | Отчасти: в 2 раундах `Abstain(rate_limited)`, ещё в 3 `Abstain(no_data)`. Ответ сервиса не хранится, число запусков до лимита не уточнено |
| Попадают ли точки check-host в antiscan и чужие фильтры | Для чужого фильтра нет: в 6 раундах обе точки подключились к порту 22. Antiscan отдельно не проверялся |
| Как часто check-host один даёт `Blocked` | В этих раундах ни разу; для вывода мало данных |
| Виден ли бан на порту 22 у живой заблокированной ноды | Не проверено: заблокированная нода не встретилась |

Возврат ноды при ложном красном Globalping одним раундом на проде тоже не проверен: на нодах с чужим фильтром Globalping не голосует. Для проверки нужна нода без фильтра.
